# Подготовка публикации Mellow House

Фактическая публикация не выполнялась. Нужны аккаунт пользователя, подключённый репозиторий и постоянная PostgreSQL. Docker не нужен для локального F5.

## Проверенный по документации путь

Официальная документация Vercel, проверенная 18–19 октября 2026: [Container Runtime](https://vercel.com/docs/functions/runtimes/container) описывает Beta на всех планах, обнаружение `Dockerfile.vercel` в корне и маршрутизацию запросов в OCI-контейнер. Доступ конкретному аккаунту и условия следует повторно проверить при публикации. C# не переносится в обычную Node Function.

1. Загрузите **содержимое папки MellowHouse** в новый приватный Git-репозиторий. Исключите App_Data, .nuget, .dotnet, artifacts, пользовательские .suo/.user и любые секреты. `.gitignore` и `.dockerignore` подготовлены.
2. Импортируйте репозиторий в Vercel. Root Directory — корень MellowHouse, где лежит Dockerfile.vercel. Отдельный frontend build, npm install и Output Directory не требуются для контейнера.
3. Проверьте, что проект распознан как Container Runtime. Если Beta недоступна, используйте альтернативу ниже. Платные услуги автоматически не подключаются.
4. Подключите постоянную PostgreSQL. Строка подключения должна требовать SSL в соответствии с документацией выбранного провайдера. Базу разместите в регионе рядом с контейнером. Не используйте SQLite внутри временного контейнера.
5. Задайте переменные окружения, затем отдельно выполните миграции и seed. После этого выполните deployment и smoke-check.

## Переменные окружения (без секретных значений)

| Имя | Назначение |
|---|---|
| `ASPNETCORE_ENVIRONMENT` | `Production` |
| `Database__Provider` | `Postgres` |
| `ConnectionStrings__Postgres` | Секретная строка подключения PostgreSQL; только настройки аккаунта/секреты хостинга |
| `PORT` | **8080**, обязательно согласовать с EXPOSE и процессом; Vercel по умолчанию ожидает 80, наш непривилегированный контейнер — 8080 |
| `ASPNETCORE_HTTP_PORTS` | 8080; при наличии PORT приложение слушает `0.0.0.0:PORT` |
| `Database__ApplyMigrations` | `false`: управляемое применение перед deployment |
| `Admin__Login` / `Admin__Password` | Секреты первого управляемого --seed, подробнее ниже |
| `AllowedHosts` | Публичный домен проекта и при необходимости собственный домен; разделитель `;` |
| `ReverseProxy__KnownProxies__0` и далее | Только подтверждённые IP доверенного proxy, если инфраструктура их предоставляет |

Приложение не включает принудительный HTTPS redirect за недоверенным proxy. Secure-cookie устанавливается при корректном HTTPS request scheme; нельзя очищать список доверенных прокси, чтобы безусловно доверять любым forwarded-заголовкам. Перед публичной демонстрацией проверьте forwarded-схему и атрибут Secure в cookies на фактическом URL.

## Схема и постоянные ключи

У провайдеров **разные** миграции: `Data/Migrations/Sqlite` и `Data/Migrations/Postgres`. SQLite-миграция не используется для PostgreSQL. Публичные миграции не запускаются при каждом холодном старте.

Из контейнера/окружения администратора с заданной PostgreSQL connection string однократно выполните:

```text
dotnet MellowHouse.Web.dll --migrate --seed
```

Либо используйте EF Core с `PostgresShopDbContext` из SDK-окружения. Подготовленный SQL в `docs/schema-postgres.sql` применяется управляемо; наполнение — отдельно `--seed`. Перед изменением существующей базы сделайте резервную копию. Seed наполняет только пустой каталог. Правки из админки не перезаписываются при повторном --seed; цены, настройки и известная себестоимость заказов зафиксированы снимками.

Ключи ASP.NET Data Protection находятся в таблице `DataProtectionKeys` той же постоянной БД. Это сохраняет cookies между экземплярами и холодными стартами. Доступ к БД должен быть ограничен; включите шифрование хранения у провайдера. Для реального сервиса добавьте защиту ключей сертификатом/KMS. Публичный демовход по телефону изолирует профиль по случайному защищённому идентификатору браузера и не открывает чужой профиль по произвольному номеру. Фиксированный 123456 доступен только в Development.

## Если Container Runtime недоступен

Разместите **то же приложение ASP.NET Core** на обычном .NET/OCI-хостинге с PostgreSQL. Vercel используйте как входной домен через внешний rewrite. В `deploy/vercel-proxy.example.json` замените YOUR-DOTNET-HOST.example своим проверенным HTTPS backend и сохраните как vercel.json отдельного proxy-проекта. Это не заменяет C# сервер локальным хранилищем браузера.

Перенаправление сохраняет единый публичный origin для Razor и API. Не кэшируйте HTML с личным состоянием, auth, API, корзины, заказы и оплату. Пример консервативно отключает CDN-кэш на всём proxy. После проверки можно отдельно кэшировать только общие изображения, CSS и шрифты с версионированием.

## Smoke-check публичного URL

- `/health` отвечает healthy; фото/шрифты локальные, HTTPS без mixed content.
- В Production вход создаёт изолированный демопрофиль, не открывает другой аккаунт по номеру.
- Соберите корзину, обновите страницу, войдите, пройдите карту и СБП: ошибка/отмена/повтор/успех без дублей.
- Перезапустите deployment: заказ и вход сохраняются в PostgreSQL.
- Проверьте cookies, CSRF, чужой заказ, отсутствие CDN-кэша персональных ответов и утечки адресов в логи.
- Проверьте 390/768/1024/1440 px, меню по якорям и reduced motion.

Контейнер и PostgreSQL в этой среде не запускались. Сгенерированные миграции и Dockerfile подготовлены, но публичный URL и инфраструктурная проверка остаются этапом подключения аккаунта.

## Редакция 2: подготовка публичной среды

- Задайте Admin__Login и Admin__Password только для управляемого первого --seed. Пароль держите в секретах, затем удалите из окружения. Локальный admin-access.json не публикуйте.
- SQL включает обе PostgreSQL-миграции, в том числе StudioV2. Применение к живой PostgreSQL здесь не выполнялось.
- Контакты, доставка и способы оплаты теперь хранятся в БД и меняются в админке; старый Cafe__DeliveryPrice не используется.
- Почтовые профили входят по хешированному паролю. Подтверждение почты и настоящую доставку писем нужно подключить перед реальной работой.
- Локальные загрузки находятся в wwwroot/uploads. Файловая система экземпляра Vercel не является постоянным хранилищем: до открытия публичной загрузки подключите object storage и серверную выдачу файлов. На обычном .NET-хостинге допустим постоянный том с резервным копированием. Исходные фото и ролик входят в publish.
- Локальный MutationGate сериализует изменения внутри одного процесса. Для нескольких экземпляров нужны проверка конкурентных оплат/возвратов на PostgreSQL и, при необходимости, блокировки и транзакционная идемпотентность в БД.
- IPaymentProvider и IMenuAssistant подготовлены; реальные ЮKassa, SMS, почта не подключены; AI использует NVIDIA.
- После подключения аккаунта повторите клиентский сценарий, роли, reset/блокировку, медиа, обновление deployment и сохранность данных на фактическом *.vercel.app.

На хостинге задайте `Assistant__ApiKey` в серверных секретах и `Assistant__Models__0=nvidia/nemotron-3-ultra-550b-a55b`, `Assistant__Models__1=nvidia/nemotron-3.5-super-vl-120b-a12b`, `Assistant__Models__2=nvidia/nemotron-3.5-lightning-30b-a3b`. Локальный App_Data/assistant-secrets.json исключён из publish и образа. Не добавляйте секрет в публичные переменные, репозиторий или браузер. Исходящий HTTPS к integrate.api.nvidia.com должен быть разрешён; live AI проверяется после подключения аккаунта. Официальная совместимость API: https://docs.api.nvidia.com/nim/reference/llm-apis.

Для новой реальной БД задайте `Samples__Disabled=true` перед `--seed`: будут 32 товара без вымышленных клиентов и истории. Не переносите учебные продажи в реальную отчётность. Флаг не удаляет существующие записи. Локальная база пользователя с примерами остаётся локальной; опубликованная рабочая БД готовится отдельно. Веб-история, изображения и каталог не требуют изменений страниц при наполнении.

Итерация 4: примените миграцию ProfileDetails до запуска. PostgreSQL SQL обновлён в deploy/postgres.sql. Admin__Email задаёт почту первого локального администратора; учётная запись входит через общую форму почты/пароля. Для существующей производственной БД задавайте уникальную почту, не переиспользуйте локальные пароли. Примеры расходов/истории не переносите в действующую отчётность. Исходящие запросы AI имеют общий предел 35 с; инфраструктура должна допускать это время и корректную отмену.
